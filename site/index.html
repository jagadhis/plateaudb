Experimental

Rust · WebAssembly · OPFS · IndexedDB-compatible

A browser database whose query time plateaus as data grows.

plateau stores your app's data in the browser's Origin Private File System and indexes every queryable field with compressed bitmaps. A query like team = 7 AND state IN (1, 2) ORDER BY updatedAt DESC LIMIT 50 costs about the size of its answer, not the size of the table. You talk to it through the IndexedDB API you already know.

Where it stands

An experiment, built in public milestones with a written pass/fail rule before every run. The engine and the IndexedDB-compatible API work end to end in Chromium, WebKit and Firefox. It is on npm as plateaudb under the MIT licence; it is pre-1.0 and not yet proven on production data.

Works today

  • IndexedDB-compatible API: databases, object stores, indexes, key ranges, cursors, transactions, events.
  • Conformance: 87 of 87 WPT-style tests pass in Chromium, WebKit and Firefox, including a key stored as -0, which comes back as -0 (from 0.3.0). Native IndexedDB passes 87 in Chromium and WebKit, 84 in Firefox.
  • Multi-key queries with store.query({where, orderBy, limit, count}) on declared typed columns.
  • Lazy, paged open: a 1M-row database opens without reading the file.
  • Put, delete and compaction, crash-safe: a crash test over 1,410 tear points passes.
  • Memory budget with eviction: default 64 MiB, 24 MiB on low-memory devices.
  • No special server headers (no COOP/COEP); the worker and WASM start themselves.
  • From 0.2.0: where OPFS, module workers or WebAssembly are missing, or in a WebKit ephemeral session, it runs on the browser's own IndexedDB (conformance matches it: 87 of 87 in Chromium and WebKit, 84 of 87 in Firefox), and plateau.backend says which one runs.
  • Several tabs at once: one tab runs the worker, the others forward to it; when that tab closes another takes over within about 15 ms, and no committed write is lost. versionchange and blocked reach every tab as natively.

Not yet

  • Blob, File, ImageData and Error values throw DataCloneError.
  • A fresh page load through the API is about 2x slower than native IndexedDB (6-10 ms against 3-5 ms).
  • In Firefox, on the IndexedDB fallback, a -0 key comes back as 0 and a held-up open sometimes gets no blocked event, as in Firefox's own IndexedDB.
  • A store that holds a -0 key written by 0.3.0 cannot be read by 0.2.0: no downgrade.
  • Pre-1.0: the API may change between minor versions.

Milestones

    How it works

    IndexedDB answers a multi-key query by walking one index and filtering the rest row by row, one async request at a time. plateau keeps a bitmap of row ids per field value, intersects them, and walks an ordered index only inside the group it needs.

    Bitmaps for every filter

    Each indexed field keeps a compressed bitmap of the rows holding each value. assignee = 12 AND label = 3 AND priority ≤ 2 becomes an intersection of three bitmaps, so the work follows the answer, not the table.

    Ordered indexes grouped by a key

    An ordered field (updatedAt) can be grouped by another (teamId). "Latest 50 in team 7" walks team 7's list from the top and stops at 50, and a count inside a range reads the range's ends.

    Lazy segments on OPFS

    Opening reads a small manifest. Columns, index blocks and rows load on first touch and are dropped least-recently-used once the memory budget is reached. Writes go to an in-memory delta and are saved as segments; compaction merges them.

    Synchronous file access in a worker

    OPFS gives a dedicated worker a synchronous file handle. The engine reads exactly the bytes it needs with no per-request promise or IndexedDB transaction cost, and the API sends each transaction's work across in one message.

    The same query, three plans

    Recorded by the benchmark at 1M rows. Q1 is "team = X AND state IN (…) ORDER BY updatedAt DESC LIMIT 50".

    Use it

    plateau is the IndexedDB API, plus one optional thing: declare the fields you filter on as typed columns, and query them with store.query. Code that never declares columns runs unchanged as a generic store.

    Install: npm install plateaudb. The package ships its worker and WASM file next to its code and names them with new URL(…, import.meta.url), so a bundler (Vite, webpack 5, Next.js) picks them up with no config, and no COOP/COEP headers are needed.

    Open it like IndexedDB

    plateau is an IDBFactory. Existing code can take it where it took indexedDB.

    import { plateau, promise } from "plateaudb";

const open = plateau.open("tracker", 1);
open.onupgradeneeded = () => {
  open.result.createObjectStore("issues", {
    keyPath: "id",
    // optional: fields you filter or sort on, as typed columns
    columns: {
      id:         "f64",
      teamId:     { kind: "u32", index: "bitmap" },
      stateId:    { kind: "u32", index: "bitmap" },
      assigneeId: { kind: "u32", index: "bitmap" },
      labelIds:   { kind: "u32_multi", index: "bitmap" },
      priority:   { kind: "u32", index: "bitmap" },
      updatedAt:  { kind: "f64", index: "ordered", group: "teamId" },
      title:      "str",
    },
  });
};
const db = await promise(open);

    Read and write with the usual calls

    put, get, getAll, count, cursors, key ranges and indexes behave as IndexedDB's do. Fields you did not declare are stored with the row.

    const tx = db.transaction("issues", "readwrite");
const issues = tx.objectStore("issues");
issues.put({ id: 1, teamId: 7, stateId: 2, assigneeId: 12, labelIds: [3, 9],
             priority: 1, updatedAt: Date.now(), title: "Fix login", notes: { any: "shape" } });
const one = await promise(issues.get(1));
    3

    Ask multi-key questions

    Filters are ANDed: eq, in and range (gt, gte, lt, lte). Add orderBy and limit, or count: true. The request's plan names the plan it chose.

    const store = db.transaction("issues").objectStore("issues");

// latest 50 open issues in team 7
const latest = await promise(store.query({
  where: [
    { field: "teamId",  op: "eq", value: 7 },
    { field: "stateId", op: "in", values: [1, 2] },
  ],
  orderBy: { field: "updatedAt", desc: true },
  limit: 50,
}));

// how many changed in team 7 this week
const n = await promise(store.query({
  where: [
    { field: "teamId",    op: "eq", value: 7 },
    { field: "updatedAt", op: "range", gt: weekAgo },
  ],
  count: true,
}));

    Tune memory and space, and follow changes from other tabs

    await plateau.setMemoryBudget(32 * 1024 * 1024); // or null for no limit
const stats = await plateau.memoryStats("tracker");  // WASM memory, cached and file bytes
await db.compact();                                 // merge segments, reclaim deleted rows
const stop = db.observe("issues", ({ stores }) => render()); // after a commit in any tab

    Typed stores take plain objects. A store without columns takes any structured-clone value IndexedDB stores, except Blob, File, ImageData and Error.

    Try live sync

    An orders list kept live from a server-sent event stream, with plateau as the local store and only the leader tab holding the stream. The server is a stand-in for an orders app's backend, with orders in memory. Edit an order, cut the stream, close the leader tab, and watch what each tab does.

    This needs a page served over http (OPFS, Web Locks and an event stream do not work from a file). Start the demo server and open this page from it:

    cd examples/live-sync
bun run build
bun server.ts --orders 1000 --poll-ms 1000
# open http://localhost:5190/site/#try

    Each frame is a tab of this origin. The first tab to start leads; the status line in each frame says which is which. An edited order moves to the top of every tab.

    Against native IndexedDB

    Same API, much faster where IndexedDB is slow: multi-key queries, counts, point reads and write commits. IndexedDB still wins a fresh page load, starts with no worker and runs in every tab.

    Against SQLite-WASM

    SQLite is the strong control: mature, with a real planner. At 100k and 1M rows plateau is 1.3-8x faster on the four queries, 3-4.5x on point reads and 6-16x on update commits, and reaches a fresh page's first answer about 4x sooner. You trade SQL for the IndexedDB API.

    Against wrappers (Dexie, RxDB)

    Wrappers add a nicer API on top of a storage engine and inherit its costs. plateau replaces the engine under the API, so a wrapper could sit on top of it. Dexie on plateau is a goal, not yet tested.

    Method and caveats

    Honest limits and what is next

    Fresh page start-up

    Through the API, a fresh page reaches its first answer in 6-10 ms against native IndexedDB's 3-5 ms. The cost is loading the API's code, starting a worker and compiling WASM. That is next (M2c).

    One machine, two browsers

    Every number here comes from one Apple M5 Max, headless, with a warm OS file cache. The benchmark numbers are from Chromium and WebKit; Firefox runs the conformance and multi-tab tests but is not benchmarked yet, and no phone has been measured.

    Generic stores are slower

    Without declared columns, values are stored as tagged JSON and queries go through IndexedDB-style indexes. It still beats native IndexedDB on most measures, by less.

    Durability and tabs

    Commits are crash-safe, and they survive the tab that runs the database closing: a transaction it was running for another tab aborts with UnknownError. A commit whose answer was lost with that tab may have landed although the transaction reports an abort. The full WPT IndexedDB suite and a fallback to native IndexedDB are planned, not built.

    Roadmap

    1. M2c API start-up: close the fresh-page gap with native IndexedDB.
    2. M2b Run the full WPT IndexedDB suite and report a pass rate.
    3. M3 A planner with statistics for queries the current rules do not cover.
    4. Fallback to native IndexedDB where OPFS is missing, Dexie on top, then a published package.
